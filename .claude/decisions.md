## 2026-07-22 — Batch drafting: don't build it, widen the pre-draft window (challenge gate)
Brief + Q's answer (AskUserQuestion): **widen the window, no batch-draft UI.**

The 2026-07-22 UX pain check surfaced `Draft`-button dead clicks on `/week` and the first read was "users can't batch-draft the week." Grounding it killed that framing: batch pre-drafting **already exists** (`predraftWeek.js`, lane `pre_draft_week`, enabled on movebetter since 2026-07-03). The real defect was its eligibility window — `plan_week=eq.${nextMonday}`, a strict equality. The moment that week became the *current* week, every still-undrafted slot in it was permanently ineligible and could only be hand-drafted one at a time.

**Evidence:** 11 of movebetter's last 66 drafts (17%) carried the `voice_audit.predrafted` marker; the owner hand-clicked the other 83%. On 7-21, five `Draft` dead clicks each landed 12–39s *before* a real draft row (linkedin/gbp/instagram/instagram/linkedin) — one person drafting 5 posts serially over 11 minutes, hitting the single-flight lock on every attempt to start the next. The 7 atoms involved had existed since early June, so pre-draft had six weeks and still never became eligible for them.

**Change:** window is now `thisMonday <= plan_week <= nextMonday`, plus `scheduled_at >= now() - 24h` so long-past slots don't burn model calls (weeks before thisMonday stay excluded, so abandoned plans stay abandoned). Validated against prod before shipping: old filter matched **0** candidates, new filter matched **1** — the current week's remaining pending slot that would otherwise have waited for a hand-click.

**Per-tick cap deliberately NOT raised.** `agent-tick` runs `*/5`, so the existing cap of 2 drains a 10-slot week in ~25 min; the binding constraint is `daily_ai_call_cap` (40), not the cap. Raising it would add spend risk without throughput.

**Kill criterion:** if by **2026-08-19** (4 weeks) the agent-predrafted share hasn't moved from 17% to **≥60%** of drafts, the window wasn't the constraint — investigate the daily AI-call cap and the `interview_id`/`scheduled_at` eligibility filters before reconsidering any batch-draft UI.

**Resolved early — 2026-08-07 (investigation, #2575, #2580):** the 08-07 weekly check-in read 27% and was trending toward MISS, which triggered the criterion's own investigation step ahead of schedule. Found: neither cap ever bound (`daily_ai_call_cap` peaked at 32/40; `predraft_failed` events: zero), and the eligibility filters correctly narrow the pool rather than wrongly excluding it. The 27% reading itself was a **metric bug** — `reviseContentItem.js`/`regradeContentItem.js` PATCH `voice_audit` by rebuilding it from scratch, silently dropping the `predrafted` provenance flag on any pre-draft that later got revised or auto-repaired. The immutable `agent_actions` ledger (write-once, at draft time) showed the true rate was **64%**, already clearing the bar. Fixed going forward in #2575; the 19 historically-clobbered rows were backfilled same-day (#2580) — ledger and live marker now agree exactly (43/43). **Criterion MET on ground truth; the window widening did its job.** No batch-draft UI needed. Full writeup: `.claude/outcome-reviews/2026-08.md` § "Pre-draft eligibility findings."

## 2026-07-25 — Answer voice gate: safety line redrawn, publish bar stays 7.5
Two clinician-facing failures on the same gate, one session, both fixed (#2344, #2346, #2347).

**What broke.** Approving a public answer failed with "Couldn't check the voice on this one" on ~1 in 3 attempts. Every failure was `no_dims_parsed` — the judge answered fine, the parser threw it away: it ran `JSON.parse` over the WHOLE reply, and the judge intermittently appends a `**Rationale:**` essay after the JSON (which also blew the 300-token cap, truncating mid-prose while the object sat complete at the top). `captionFidelityRubric.js` already had first-object recovery for exactly this; its sibling answer rubric, written later, never got it — **one primitive, two copies, drifted.** Now a single shared `extractJsonObject()` both import.

**Second failure, only visible once scoring worked:** `gate: 'unscored'` rendered nothing — no chip, no banner, green Approve. A fail-closed gate with no user-visible reason is a dead end, not a safeguard. Now a persistent banner that says plainly it isn't their writing, plus a `recheck` action that re-scores without publishing.

**Calibration (Q's call).** The safety dimension said only "NEVER prescribe treatment or dosing" with no general-vs-individual line, so it scored ordinary public teaching as prescription: *"short, quick steps keep you over your feet"* → safety 5, holding a sound answer at 6.0. Q: *"short quick steps is a suggestion or guidance"* — shoes "a little more prescriptive" but still guidance. **Fixed the grader, not the drafts** — tuning writing to a mis-drawn line teaches Bernard to write evasively. Line is now GENERAL TEACHING (expected, never penalized) vs INDIVIDUAL INSTRUCTION (unsafe).

Old→new, 3 samples each: every real answer's safety rose (running form 6.67→9.0; others 8–9→9–9.67) while **all three adversarial probes — diagnosing the reader, dosing/personal plan, fabricated study — stayed at safety 1 and blocked.** More accurate, not weaker; the probes are the proof, and any future loosening must re-run them.

**Decision: the 7.5 bar stays.** Running form now scores 7.33 — held by 0.17, on faithfulness grounds ("the calf's job is to absorb the landing" oversimplifies the whole-body torque emphasis). Q reviewed and called it **a fair hold**. The bar was deliberately not moved while fixing the grader; a gate constant on public medical content is a clinical judgement, not a bug fix.

**Revisit-by: 2026-09-30.** If held answers pile up unresolved (queue `voice_audit->>'gate' = 'held'` aging >14d) or clinicians routinely override by rewriting to game the score rather than to improve the answer, re-examine the bar. If nothing is held for a month, the bar is too low to be doing work.

## 2026-07-25 — The answer voice check advises; it never blocks (reverses F16 Phase 1)
Same day the 7.5 bar was confirmed (entry above), Q edited the running-form answer in light of Bernard's feedback, was still refused, and called it: *"Bernard should never STOP a post that is edited by a person who considers the feedback from Bernard. It should just advise against it with good reason and scoring then leave a back door."* **This reverses the hard gate shipped in F16 Phase 1 — deliberately, with the reasoning below, not by drift.**

**The measurement bug under the product call.** `said_fidelity` scores text against the clinician's captured practice memory. That is the correct reference for an AI first draft. It is the WRONG reference the moment a human edits, because the clinician IS the source of truth — so the judge cannot distinguish "the model invented this" from "the doctor just taught something new", and it reliably reports the second as the first. Concretely: Q wrote a passage on hip flexion driving hip extension; the judge returned *"invented mechanical specifics … not in the source material"* and held it at 7.3. The corpus was stale, not the doctor wrong. **A metric that cannot tell new teaching from fabrication must not hold a gate over the person doing the teaching.**

Second argument, independent of the bug: blocking a licensed clinician from publishing his own words, on his own site, under his own name is the wrong default — and it fed the approval backlog that is the product's actual bottleneck (49+ open drafts, publish-silence past the 7-day line).

**Chosen (Q, from three options): always advisory, never blocks** — over the recommended "advisory only after a human edit" and over "hard floor on safety". Approve always works; the banner keeps the full score, dimensions and verbatim critique; amber replaces destructive red; the button reads "Publish anyway" below the bar so an override is deliberate, not reflexive. Overrides are recorded (`published_over_flag`, `overridden_at`, full score at that moment; `published_without_check` when the check couldn't run) — the audit trail replaces the wall.

**New-teaching capture (migration 187).** Publishing over a faithfulness flag queues a `topic_backlog` row (`source: 'answer_gap'`, judge's flag text as rationale, idempotent per answer). The passage Bernard failed to recognise is exactly the teaching it hasn't captured, so the false positive feeds the interview flywheel instead of being discarded.

**Accepted risk, stated at decision time:** this also unblocks an UN-edited draft — a first-pass answer that fabricates a study can now publish in one click, where the gate used to stop it. Q was shown this consequence in the option text and chose it anyway. The fallback if it bites is the middle option (voice advisory, hard floor on safety only), a small change from here.

**Revisit-by: 2026-09-30** (same date as the bar entry, review together). Kill criteria: (a) anything factually wrong or unsafe reaches the public site via a one-click override — revert to the safety-floor option immediately; (b) if `published_over_flag` is set on the large majority of publishes, the bar is mis-set rather than the gate mis-designed — recalibrate rather than re-block; (c) if `answer_gap` topics accumulate `pending` and never get interviewed, the capture half is theatre — either wire it into interview prompting or drop it.

## 2026-07-25 — Templates are authored in the real editors, not a template-editing screen
Q, cutting off a build that was about to mirror the photo-templates settings page for video: *"Shouldn't the photo templates and video templates just use the existing photo and video editors to make changes and creations that can then be save or edit templates?"*

**Chosen: author in the editor, manage in the library.** A look is dialled in on a real clip or carousel and promoted via **Save as … template** (VideoEditor Captions panel, #2371; SlideEditor Theme panel, #2376). `/settings/video-templates` and `/settings/photo-templates` browse, rename, delete and choose — they do not style.

**Rationale, and it is stronger than "less UI to build".** Photo templates are trustworthy because their preview *is* the publish renderer. Video renders server-side in ffmpeg, so a template-editing screen would have needed either a canvas mirror (drifts) or a server round-trip per keystroke (slow). Authoring in the editor removes the question: the editor already renders the real thing. This session had already shipped two mirror-drift bugs — the caption Size control previewing identically for Medium and Large while baking 1.0× vs 1.35×, and a glow preview left showing an accent halo after the bake moved to a dark one — so the hazard was demonstrated, not theoretical.

**What this cancelled.** A server-rendered-sample-frame preview subsystem, already scoped and chosen, was deleted from the plan before it was built. The data-model work it sat on (`workspace_video_templates`, configs replacing an enum, the renderer reading them — #2369) was unaffected and shipped.

**Rotation was dropped in the same move.** Deterministic rotation across four built-ins made "which look did a human keep" measurable at N=5, which only works for a small FIXED set. Once a workspace can author templates, rotation renders reels in a look nobody chose. Resolution is now explicit: workspace pin → its default template → built-in `hook_card`; the template used is recorded on `media_assets.variant_label` so usage stays measurable.

**Accepted risk, stated at decision time:** the style/content split in each capture module is **unvalidated** — the boundaries were chosen by reasoning, not by watching anyone use it. The photo one is the weaker of the two: the editor sets eleven per-block properties and the template schema holds five, so six are named-but-dropped. If that split is wrong the symptom is quiet — a template that "doesn't look like what I saved" — not an error.

## 2026-08-10 — Render at 1080-class, not 4K: an undocumented ceiling made explicit

**Trigger.** Chasing a 3.1 GB 4K master that was blocking the reel queue, Q asked whether any social lane can use 4K, and whether that ceiling is a platform limit or ours. Neither the code nor the decisions log answered it.

**Finding.** `postFrames.js` carried "Ratios verified against current platform guidance 2026-07-22" — but that sentence covers the RATIOS only. Each ratio has a real, cited rationale (Meta's March 2026 9:16 consolidation; Google clipping both portrait and 16:9 so only 4:3 survives; TikTok letterboxing 1:1 and 4:5). `FRAME_PIXELS` sat directly beneath it with **no rationale, no citation, and no verification** — a 1080-class ceiling that read like a researched platform constraint and was in fact an unexamined default. That adjacency is the actual defect: a verified claim lending false authority to an unverified one.

**Chosen (Q): stay at 1080-class.** No visible gain today. Real footage is 4K at ~96 Mbps, so rendering above 1080 costs render time and upload bytes on every clip. The one lane where 4K provably reaches a viewer — YouTube long-form — does not use this table at all: the YouTube copy lane ships the ORIGINAL asset, so the master already arrives untouched (bounded only by `YOUTUBE_MAX_UPLOAD_BYTES`, empirically 2.5 GB). 4K still earns its keep at CAPTURE, giving the reframe pass latitude to punch in without softening a 1080 output — we downscale on the way out, never ask anyone to film smaller.

**Recorded honestly as an assumption.** "Platforms accept larger uploads but re-encode short-form back toward 1080" is stated in the code as an ASSUMPTION, not fact — nobody has measured it end to end. Writing it as verified would repeat the exact mistake this entry documents.

**Trap for whoever raises it.** Two edits, not one: `brandRenderVideo.js` independently caps the large-source ingest proxy at `scale=w=1920:h=1920` before the render runs, so changing `FRAME_PIXELS` alone moves nothing for precisely the 4K sources you would be doing it for.

**Revisit if** a platform starts serving short-form above 1080 in a way a viewer can see; a clip is reported as soft or over-compressed; or we add a lane that COMPOSITES for a 4K-served surface (compositing for YouTube long-form rather than passing the original through would qualify). The honest test is empirical — push one 4K render through bundle.social and compare what comes back — so treat the assumption as unproven until someone runs it. **No revisit-by date: this is a standing default, not a bet with a clock.**

**The 4K future, addressed** (Q's immediate follow-up to the above: *"4K is how people film — it's also how they will or eventually will post"*). The pipeline is three layers: 4K MASTERS (untouched, kept forever) → a per-asset DERIVED render intermediate (regenerable, sized to the current output spec) → per-lane RENDERS (`FRAME_PIXELS`). The 1080 ceiling lives only in the derived layers, so "eventually posts in 4K" is a parameter change — add 4K frames (both edits) and regenerate intermediates — not a rework, and nothing filmed today is diminished by it. Two consequences worth pinning: (a) a 4K-output era makes per-asset derivation MORE necessary, since decode cost scales with resolution — paying it once per asset instead of once per segment-attempt matters more at 2160 than at 1080 — and true 4K composited renders likely outgrow the 300s serverless wall entirely (a render queue/worker becomes the shape; decide then, not now); (b) capture bitrate ≠ delivery bitrate: the 3.1 GB / 96 Mbps master re-encodes at 4K delivery bitrate (~⅓ of capture; verify the exact target against provider guidance when built) to ~1.1 GB — full 3840×2160, under bundle.social's 2.5 GB YouTube ceiling. The derived layer is what makes that file postable at 4K AT ALL; today it exceeds every path.

## 2026-08-11 — Vercel's project-wide function timeout ceiling silently clamps a route's own maxDuration

**What happened.** Chasing the 19-day reel-render outage (see the two entries above), a route's `export const config = { maxDuration: 800 }` deployed clean and still 504'd at exactly 300.29s in production — with no warning anywhere in the build or deploy output. Root cause: Vercel projects carry a SEPARATE, project-wide ceiling (`defaultResourceConfig.functionDefaultTimeout`, the "Function Max Duration" field under Settings → Functions in the dashboard) that a route's own `maxDuration` can only ever undercut, never exceed. This project's ceiling had never been raised past 300, so every route in Bernard was silently capped there regardless of what any individual file declared.

**How it was found — reading the actual enforced value, not trusting the deploy.** `GET /v13/deployments/:id` → `config.functionTimeout` shows what a given deployment ACTUALLY enforces; this is the ground truth, distinct from what any route file requests. `GET /v9/projects/:id`, walked recursively for any key containing "duration"/"timeout", surfaced `defaultResourceConfig.functionDefaultTimeout` as the project-level source of that value.

**Fix.** `PATCH /v9/projects/:id` with `{"resourceConfig":{"functionDefaultTimeout":800}}` — Q approved explicitly (2026-08-11) because it's a project-wide change (every function's ceiling moves, not just the one route in question), matching the "changing account settings" confirm-first bar. Then a FRESH BUILD, not a redeploy/alias-promote of the existing one — the already-built deployment was compiled under the old ceiling and a straight promote would not have picked up the raise. Confirmed by re-reading `config.functionTimeout` on the newly-built deployment before re-testing anything downstream.

**Generalizes.** Any future route that needs `maxDuration` above whatever this project's ceiling currently is will hit the identical silent clamp — a clean build, no error, and a 504 at the OLD number. Before raising a route's `maxDuration` and trusting it, check the live deployment's `config.functionTimeout`, not just the file you edited.

### Addendum 2026-08-11 — the project ceiling was never the whole fix: `auto-reel-week.js` was in the CONSOLIDATED app the whole time

**What happened.** Investigating why `agent_actions.kind='footage_needed'` had zero rows ever, real prod logs from a manual trigger showed `Vercel Runtime Timeout Error: Task timed out after 300 seconds` — on this exact route, on THIS deployment, whose own `GET /v13/deployments/:id` → `config.functionTimeout` read **800**, per the fix above. The project-ceiling raise was real and correctly applied; it just wasn't the constraint actually in force.

**Root cause.** `cron/auto-reel-week.js` lived under `api/_routes/`, which means it isn't its own Vercel function at all — every file there gets mounted as one Express route inside the single consolidated app at `api/index.js`, and `api/index.js` declares its OWN `export const config = { maxDuration: 300 }` at the top of the file. That line — not the project ceiling, not this route's own `config` export (which was simply never read, because this route was never its own function) — is what capped every invocation at 300s. The 2026-08-11 entry above raised the DEFAULT ceiling for functions that don't set their own `maxDuration`; `api/index.js` sets one explicitly, so the default never applied to it.

**Fix.** Moved the file to `api/cron/auto-reel-week.js` (top-level, outside `api/_routes/`) and added it to `KEEP_FILES` in `scripts/api-consolidation.config.mjs`, matching the existing pattern for every other render-heavy handler (`api/media/*.js`, `api/editorial/render-*.js`) — Vercel's filesystem routing wins over the `vercel.json` `/api/(.*)` rewrite, so no rewrite change was needed. The file's own `maxDuration: 800` now actually governs its own function.

**The tell, if this recurs elsewhere.** A route 504ing at exactly 300s despite its own `config.functionTimeout` reading a higher number on the live deployment (i.e., the fix above's own check passing) means the constraint is one layer further in: check whether the route lives under `api/_routes/` (consolidated, governed by `api/index.js`'s `maxDuration`) or is its own standalone file under `api/`. Only a standalone file's own `maxDuration` is ever actually enforced independently.

**Generalizes.** Any `api/_routes/**` cron or handler that starts doing real render/long-running work inherits `api/index.js`'s 300s ceiling no matter what its own file says — that ceiling can only be raised for ALL ~250 consolidated routes at once (a much bigger blast radius than one route), so the correct move for a genuinely slow handler is always extraction to its own file via `KEEP_FILES`, not editing `api/index.js`'s `maxDuration`.
